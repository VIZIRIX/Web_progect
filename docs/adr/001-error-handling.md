# ADR 001 — Обробка помилок: `AppError` + глобальний `errorHandler` (RFC 9457)

## Статус: прийнято (2026-11-22)

## Контекст

До рефактору всі маршрути (`routes/booking.routes.ts`, `room.routes.ts`,
`settings.routes.ts`) містили `try/catch` + розбір помилок за текстовими
рядками:

```ts
throw new Error('TIME_CONFLICT');
// ...
if (error.message === 'TIME_CONFLICT') { ... }
```

Це робило код повторюваним і уривчастим: одна помилка впливала на кілька хендлерів.

## Розглянуті варіанти

1. Залишити обробку помилок у кожному роуті (те, що було) — не масштабується,
   рядки помилок легко сплутуються.
2. Власні коди помилок (`enum ErrorCode { ... }`) передавати через `res.status(...)`.
   — гарно, але клієнту довелося б парсити семантику; немає одного формату.
3. Винести обробку в глобальний middleware `errorHandler` + типізована помилка
   `AppError` — один місце відповіді на помилки, типізація на межі.

## Рішення

1. Усі помилки кодуються класом `AppError` (`api/errors.ts`) з полями
   `status` (HTTP-статус) + `title` (короткий текст) + повідомлення.
2. Один middleware `errorHandler` (останній у `app.ts`) відповідає на
   `AppError`: `Content-Type: application/problem+json` (RFC 9457) з полями
   `type`, `title`, `status`, `detail`, `instance`.
3. Помилки не `500` не містять стектрейсу (логуються через winston замість).
4. Валідація (валідатори у `validators/`) бросає `AppError` з відповідними
   статусами (400/401/404/409) — єдиний шлях відповіді на вади.

## Наслідки

- Клієнтський код знає стабільний формат: `data.detail ?? data.title`.
- Тестування `AppError`/`errorHandler` — один файл (`api/errors.test.ts`).
- Клієнтський код не залежить від реалізації роутів.
- Недолік: OpenAPI-специфікація повинна описувати саме RFC 9457 (`Problem`).
