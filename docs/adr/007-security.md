# ADR 007 — Захист від атак: helmet, rate-limit, CORS-allowlist, парольна політика

## Статус: прийнято (2026-11-22)

## Контекст

Безпечність (критерій 4 — 10 балів):
- без helmet, rate-limit, без валідації паролів, без обмеження CORS,
- `cors()` дозволяв `*`.
- Паролі хешуються `bcryptjs` — вже есть.

## Розглянуті варіанти

1. Нічого не робити — 10/10 балів під критерієм 4 неможливі.
2. helmet + rate-limit + CORS-allowlist + політика паролів — лаконічні міри,
   потребують нових залежностей: `helmet` 8.1.0, `express-rate-limit` 8.2.0.

## Рішення

- **helmet()** — стандартні заголовки безпеки (HSTS, CSP за замовчуванням).
- **express-rate-limit**: 100 запитів / 15 хв на IP — для `/api` всього (простіше,
  і покриває публічні точки: register/login).
- **cors({ origin: process.env.CLIENT_ORIGIN || 'http://localhost:5173' })** —
  дозволений лише фронтенд; в compose: `http://web_project_frontend:5173`.
- **Політика паролів (сервер)**: мінімум 8 символів, хоча б одна літера
  та одна цифра — на `POST /api/register` + `/api/login`.
- JWT-токени у заголовку `Authorization` (Bearer), `expiresIn: '24h'` —
  не змінювати (контракт з клієнтом).

## Наслідки

- HTTPS — налаштований на рівні хостингу (deploy → TLS cert).
- Секрети — паролі в `.env` роблені гідними в першу чергу (7 кращих, 8 найгірших).
- Клієнт: `apiFetch` додав `data.detail ?? data.error` — відповідно до ADR 001.
- Перед захистом: змінити паролі seed (admin → `Superadmin123!`).
