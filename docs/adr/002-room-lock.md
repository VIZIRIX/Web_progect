# ADR 002 — Блокування комнати при створенні/перенесенні броні (advisory lock)

## Статус: прийнято (2026-11-22)

## Контекст

Два паралельні запити `POST /api/bookings` (або `PATCH /api/bookings/:id`)
на одну комнату — обидва проходять перевірку перетину часів
(`booking.findFirst({ startTime: {lt: end}, endTime: {gt: start} })`) і можуть
створити перекриєдуючі броні. PostgreSQL-теж не підтримує виключені обмеження
для діпазонів (exclusion constraints не підтримується Prisma).

## Розглянуті варіанти

1. Послідовність з `SELECT ... FOR UPDATE` на записі комнати — lock комнати
   при першому `SELECT`, далі `findFirst` без проблем бо lock-працює.
2. Повторні спроби (retry loop) з `findFirst` — потребує зовнішнього
   розподіленого локатора чи базового.
3. `pg_advisory_xact_lock` — методичний вибір для конфліктів на сутностях
   (послідовні локації без очікування записів).

## Рішення

Використовувати `pg_advisory_xact_lock(74123, roomId)` у транзакції
(`services/booking.service.ts` → `lockRoomForUpdate`), тоді як усі
перетини-перевірки й всі `create/update` — в одній транзакції.

## Наслідки

- Гарантовано: дві броні однієї комнати перетинаються (за умовочкою).
- `DELETE /api/bookings/:id` не бере lock — видалення не може конфліктувати
  (отримує поточні `startTime/endTime` через `findUnique`).
- Константа `LOCK_NAMESPACE = 74123` — тільки тут, з коментарем.
